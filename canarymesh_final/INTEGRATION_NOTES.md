# CanaryMesh integration notes

## Files changed

### Backend
- `backend/main.py` connects dataset replay, device ML, SQLite, MQTT publishing, WebSocket state, alerts, isolation, sanitization, health verification, and reconnection.
- `backend/database.py` adds SQLite-backed telemetry, MQTT logs, dataset metadata, replay events, alerts, and decisions.
- `backend/dataset_loader.py` downloads/imports ToN-IoT CSVs and rebuilds deterministic replay indexes from SQLite.
- `backend/mqtt_service.py` publishes the exact dataset-backed JSON payload to a real MQTT broker when available.
- `backend/sanitizer.py` implements source blocking, queue purge, model restoration, and health verification.

### ML / FL
- `ml_federated/node_manager.py` trains one Isolation Forest per mapped device from normal benchmark rows and computes anomaly, persistence, feature-deviation, and policy risk scores.
- `ml_federated/fl_engine.py` aggregates local Isolation Forest offset parameters and measures accuracy on held-out labeled benchmark rows.

### IoT / deception
- `iot_cybersecurity/honeypot.py` is deterministic and controlled. There is no random background attacker.
- `iot_cybersecurity/mqtt_broker.py` is retained only as a compatibility wrapper. Runtime MQTT publishing is handled by `backend/mqtt_service.py`.

### Frontend
- `frontend/src/useWebSocket.js` now performs initial REST hydration and then maintains live WebSocket state.
- `frontend/src/App.jsx` exposes a Devices tab rather than a user-facing Nodes tab.
- `frontend/src/components/NodesTab.jsx` is the device list implementation despite the legacy filename.
- `frontend/src/components/Dashboard.jsx` shows the database-backed pipeline, measured risk, and controlled attack replay.
- `frontend/src/components/MQTTTab.jsx` displays the exact SQLite-backed publish records and transport status.
- `frontend/src/components/FLTab.jsx` displays measured evaluation and model update participation without calling the quantity a gradient.
- `frontend/src/components/shared.jsx` displays measured features, model evidence, benchmark label, MQTT payload, risk explanation, and the four-phase recovery controls.

## What is genuinely real in this version

- Benchmark data: UNSW ToN-IoT rows are the telemetry source when the CSVs are present/downloadable.
- Database: the runtime replay source is SQLite after import.
- ML score: generated by the Isolation Forest fitted on benchmark normal rows.
- Risk: computed from measured ML/evidence signals, not from the benchmark label.
- MQTT: a real network publish occurs when a reachable MQTT broker is configured.
- Audit: alert, decision, replay, telemetry, and MQTT records are persisted in SQLite.

## What remains a controlled demo abstraction

- The displayed industrial device identities are project aliases mapped to benchmark subsets.
- The attack demonstration replays a labeled benchmark row instead of exploiting a live target.
- Honeypot probes are controlled UI-triggered events.
- Network quarantine is represented as an application-level deny-list action. Production enforcement belongs in approved OT firewall/ACL/NAC/segmentation controls.
- The current FL implementation is compact offset aggregation. It is not a full Flower server/client deployment.

## Frontend connection verification

After starting the backend and frontend, Chrome DevTools → Network should show:

```text
/api/state
/api/mqtt/recent
/api/dataset/attack-types
/ws
```

If `/api/state` returns the same `devices` objects that the dashboard shows, the ML/backend-to-frontend connection is active. If the UI is stale while the API values change, inspect the WebSocket for `state_update` messages.
